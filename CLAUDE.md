# Agent Skills

## Audience

The skills and agents in this repository are consumed operationally by agentic frameworks (AI coding agents, copilots, and autonomous developer tools).
Every piece of guidance must be written so that an agent can act on it without human interpretation.

When writing or editing content, follow these principles:

- **Be prescriptive, not descriptive.**
  Tell the agent what to do, not explain concepts.
- **Make decisions enumerable.**
  Provide numbered decision processes, lookup tables, or explicit criteria.
- **Include code examples for every actionable rule.**
  Show both correct and incorrect patterns.
- **Avoid subjective conditions.**
  State concrete, testable criteria.
- **Keep rules self-contained.**
  Each file must make sense on its own.

## Repository Structure

Skills live in `skills/<category>/<name>/SKILL.md` across 7 categories.
Agents live in `agents/` since they need their own model and tool configuration.

Type markers (by primary entry point — all three are technically model-invocable via the `Skill()` tool when `disable-model-invocation: false`): `auto` = description aggressively auto-triggers on natural language; `/` = primary entry is the slash command, description does not auto-trigger; `Skill()` = primary entry is being called by another skill / workflow.

### `quality/` — code, tests, plans, AI apps

- `ai-engineering` (`/`) — LLM/AI app review across 13 concerns (prompts, caching, RAG, agents, evals, safety, observability)
- `code-quality` (`auto`) — readability, complexity, maintainability. Four modes: `plan` (validate a plan), authoring (default), `review` (findings only), `simplify` (review-then-apply for end-of-feature cleanup — auto-applies Class M refactor recipes behind `confidence(code) ≥ 90 %` + scoped fast-check, with revert-on-failure). Class M/J taxonomy lives in [`refactor-recipes.md`](./skills/quality/code-quality/rules/refactor-recipes.md#recipe-class--mechanical-vs-judgment) and is guarded by L1 G7
- `confidence` (`auto`) — multi-signal confidence gate for `plan` / `code` / `analysis`; deterministic rule caps LLM score at 89%
- `eval-iterate` (`/`) — drives a failing AI/LLM eval (an L2 behavioral suite, a golden-set/LLM-as-judge eval, or any eval gating a PR) to a real green. Classifies each failure as `code-bug` / `eval-bug` / `flaky` / `unsure` (composes `ai-engineering`'s evals concern), fixes the minimal cause, then requires two consecutive passing re-runs before calling it `confirmed-green` — a single lucky pass never counts. Hard-capped at 5 iterations, never raised. Any edit to the eval itself (assertion, threshold, golden-set item, judge prompt) is gated on `confidence(analysis) >= 90%` plus a logged rationale and never a silent fix-to-pass — the same executor-immutable / check-gaming-forbidden spirit as `checks.yaml`, adapted for evals rather than copied verbatim. Composes `ai-engineering`, `confidence`, and `verify-behavior`'s `change` mode rather than reimplementing diagnosis, scoring, or execution
- `severity` (`auto`) — severity/blast-radius gate for `finding` / `bug`; the orthogonal axis to `confidence` (how bad if real, vs is-it-real). Emits a lowercase `critical`/`high`/`medium`/`low` tier from a fixed axis rubric (impact, blast radius, likelihood, reversibility, capped by reachability), then one **executable** path floor (auth/billing/migration/infra/secrets globs) plus **heuristic** escalators (data-loss, security, concurrency shapes) — both skipped on test/fixture/generated/reverse-migration paths so they never inflate non-production code (only the path floor is deterministic; the escalators are LLM-judged, and the skill says so). Policy-free: it emits the tier and a `(blocking)` crosswalk (`critical`/`high` ⇒ blocking) but owns no threshold numbers — the consumer (`review-config.md`, `rubric-composition.md § Severity mapping`) does. Consumers: `pr-reviewer` severity-aware inline bar, `fix-bug`/`batch-linear-tickets` triage order, `ci-auto-fix` escalation. In `pr-reviewer` the severity-aware bar is **on by default** (medium anchors the profile's historical 80; high/critical lower, low higher), is shown inline as a `<prefix> (<tier>):` label (e.g. `issue (high):`) and a per-severity glyph breakdown in the report, and the emitted tier is recorded per outcome (read from the label) → the `reviewer-comment-relevance` record's `severity` field. Regression-tested by the `severity-tiering` L2 suite
- `critical` (`auto`) — adversarial pre-mortem with mandatory steelman alternative. Never iterates
- `measurable` (`auto`) — ensures a delivery is measurable and its regressions are visible. Classifies each changed path (`web`/`mobile`/`api`/`worker`/`infra`/`shared-lib`, reading a committed Observability Profile when one exists) and requires the matching signal: a RUM/analytics event for user-facing web/mobile changes (delegates event design to `rum-tracking`), an OTel span + RED metric + structured error log for API/backend changes (delegates to `otel-instrumentation`/`otel-semantic-conventions` when installed), and — for every signal, either category — a named regression detector (existing dashboard/check rule, or an explicit propose-via-Dash0-chat note); never creates dashboards/alerts itself. Four modes: `guide` (default, advisory), `implement` (writes/delegates instrumentation), `audit` (read-only coverage report; **advisory by default** — `--strict` escalates `missing` findings on user-facing/API paths to blocking, `unlinked` findings never block), `setup` (first-time interview recording the telemetry stack and, for monorepos, a path-glob → package-kind → stack map, persisted via `persistent-memory`'s `project-shared` tier as a committed Observability Profile — see [`templates/observability-profile.template.md`](./skills/quality/measurable/templates/observability-profile.template.md)). Wired into `autonomous-workflow` at three points: Phase 3 [Observability Trigger](./skills/workflow/autonomous-workflow/rules/phase-3-implementation.md#observability-trigger) authors coverage while implementing; Phase 4 [Observability Gate](./skills/workflow/autonomous-workflow/rules/phase-4-testing.md#observability-gate) audits it, advisory by default, opt into hard-blocking via `--observability-strict` (mirrors how `critical`/`optimize-approach` shipped opt-in/quiet rather than hard-blocking on introduction); Phase 7 [Observability Recheck](./skills/workflow/autonomous-workflow/rules/phase-7-ci-gate.md#observability-recheck) re-audits the current head after `ci-auto-fix` and the post-CI `review-loop` pass settle — both mutate code after Phase 4 already ran and can silently strip coverage it confirmed — fixing and re-checking once under `--observability-strict` before escalating, never a second stuck-loop. Also the fourth default-on `pr-reviewer` lens (Step 2.4e) via [`agents/shared/rules/measurability-review.md`](./agents/shared/rules/measurability-review.md) — `audit` mode only (the reviewer is read-only, so a lens that instrumented the diff would be authoring the change it judged), gated behind **two** quiet-exit conditions so the lens is worth having on by default (a `web`/`mobile`/`api`/`worker` path, **and** new or changed observable behaviour — a rename or a behaviour-identical refactor fails gate 2 by construction), mapping `missing` → `issue:` (strict, new failure mode) / `suggestion:` (else), `unlinked` → one aggregated `suggestion:` (strict) / `nitpick:` (advisory), `pass` → nothing at all. Strict is the **default**: a `missing` on a new failure mode reaches `FAIL_REASONS`, and a repo opts **down** with `measurable: advisory` in review-config (or `--measurable-advisory`) to keep every finding out of the verdict; `unlinked` never blocks and is never an `issue:` under either level. `--no-measurable` opts out. Its seam with the reviewer's own [`telemetry.md`](./agents/pr-reviewer/rules/telemetry.md) is explicit and one-way: that rule reads what the touched code did **yesterday** (an exposure input to priority), this lens asks what the change will show **tomorrow**, and the single permitted composition is that a `missing` finding on a high-`traffic_band` path says so — raising priority, still never blocking. Guarded by L1 `G42`
- `optimize-approach` (`Skill()`) — the fourth review lens: "is this the most optimal approach for its intent, and if not what is?" Judges four axes (codebase-fit, simplicity, performance, robustness) at the **approach level** with anti-overlap guards (defers line-level to `code-quality`, failure modes to `critical`, intent/system-fit to `holistic-review`) + a materiality bar; quiet early-exit stays silent when optimal. Three modes: `report` (proposal), `apply` (gated approach rewrite behind `confidence(code) ≥ 90 %` + scoped check + revert-on-failure; own-work only), and `plan` (approach review at plan time — consumes the Existing Code Survey, returns plan-level proposals, no code). Default-on lens in `pr-reviewer` (report-only — never applies in any relation), `polish` (apply), and `aw-planner` Phase 1 (`plan`, default-on Full Mode, bounded re-plan) via [`agents/shared/rules/optimality-review.md`](./agents/shared/rules/optimality-review.md) (Step 2.4c) and [`skills/quality/optimize-approach/rules/plan-mode.md`](./skills/quality/optimize-approach/rules/plan-mode.md); `--no-optimize` opts out. Never blocks the verdict/gate. Self-improvement: `optimize-approach-lessons` fast tier (read O0 / write O5) calibrating the optimal/suboptimal bar + apply-safety + plan-time judgment; promotes to `diagnose`
- `polish` (`/`) — re-runnable pre-PR branch quality gate; thin orchestrator that composes the `review-loop` skill (calls `pr-reviewer` in self mode — read-only, findings surfaced) and `code-quality` simplify (apply Class M refactors). Modes: bare → full (review then simplify), `review`, `simplify`, `optimize` (standalone approach-rewrite pass), `quick` (light mechanical pass). Commits each pass separately (`--no-commit` to skip). `/create-pr` delegates its post-draft quality loop to `review-loop` — full pass by default; `--no-review` → simplify only, `--no-simplify` → review only, `--quick` → light pass, `--no-quality` skips, `--no-optimize` skips the optimality lens
- `review-loop` (`Skill()`) — thin convergence orchestrator: calls `pr-reviewer` (self mode, read-only) → `implement-suggestion --resolve-all` (apply findings **and** reply-to-and-resolve non-fix threads) → `Skill("polish", "simplify")`; repeats up to N=5 iterations, converging until every review thread is resolved via fix OR reply (answered question / recorded rationale) — only genuine human-judgment flags stay open (the no-green-wash safety valve). On convergence it refreshes the PR description via the shared [`description-contract.md`](./skills/delivery/create-pr/rules/description-contract.md) (single source of truth with `create-pr`) and, best-effort, notes the linked Linear ticket (`--no-refresh` opts out). Anti-circularity: never calls `Skill("polish")` or `Skill("polish", "review")` — only `simplify`. Used by `polish`, `create-pr` (post-draft), and the autonomous-workflow Phases 6–7. **CI convergence (v1.3.0):** sub-step D reads check state after each iteration's push (stateless `gh pr checks`, never a watch) and delegates a red mechanical failure to `ci-auto-fix`, capped at 2 handoffs per run — so convergence means zero open threads **and** CI not red; `--no-ci` opts out and is passed by `create-pr` Step 6.5 and `autonomous-workflow` Phase 7, which own the per-PR CI budget themselves (each counts its own handoffs inside its own invocation, with no state carried between them; phase-7's new Step 2.5 re-checks CI after the loop pushes). **`--external-review` (v1.3.0):** sub-step A waits on the shared [`review-activity-poll.md`](./agents/shared/rules/review-activity-poll.md) for an out-of-process reviewer (another agent / review bot) instead of dispatching `pr-reviewer` — `POLL_ERROR` aborts and is never read as "reviewer quiet"; also the graceful-degradation path where the harness exposes no sub-agent dispatch tool. `--interval S` (clamped 540) sets the poll bound. **Caller contract (v1.4.0):** the loop is an orchestrator whose first sub-step is a delegation, so it must be invoked at the **top level** of a session that still holds a sub-agent dispatch tool — dispatching it into a sub-agent (which cannot delegate further) spends the delegation budget one level too high and the loop can only skip at iteration 0. A caller limited to one dispatch passes `--external-review` **deliberately**; the loop never invents it. The nested-dispatch skip has its own stop-reason token, distinct from the no-dispatch-tool one and never reported as `report-only`, and one absent-dispatch return is conclusive (no retry). **The availability check is a CAPABILITY test, never a tool-name test (v1.6.0):** the dispatch tool is `Task` in the Claude Code CLI and `Agent` in the Claude Agent SDK harness behind Claude Code on the web, so the prior literal-`Task` precondition skipped the review on every cloud session that in fact held the capability — a self-concealing failure, since a skip is a documented legitimate outcome. Also v1.6.0: exits set an explicit `STOP_REASON` the report reads, replacing an `ITERATION == CAP` test that reported report-only runs (`--no-feedback` forces `CAP=1`) and last-iteration convergences as "cap reached"; and the sub-step A claim that the loop "always ENDS on a review pass" is corrected — the no-progress guard and the cap both fire after a push.

### `testing/` — E2E and fixture tooling

- `e2e-testing` (`/`) — spec-first Playwright Test Agents loop; locator ladder; `data-testid` source diffs; 3-attempt heal cap

Validation is empirical, not predictive: every new locator must resolve against source (static grep) or the live app (`locator.count() ≥ 1`) before commit, and the fixed test must pass 3 consecutive local runs before the single push. CI watch ratifies. Refuses `.skip` / `.fixme` / `waitForTimeout`. Two modes: `stabilize` (default) and `optimize` (report-only, ranks slow-action wins by measured ms saved, no commits). Self-improvement: `e2e-pr-stabilizer-lessons` fast tier (read Phase 4 / write Phase 7, `stabilize` only) — `global` scope holds universal P1–P6 race-shape→fix mappings, `repo::` scope holds app-specific locator robustness; **writes are gated on the Phase 7 telemetry ratification, not the local 3-pass streak**; promotes to `diagnose`
- `preview-spec` (`Skill()` + `/`) — makes a UI PR autonomously verifiable. The agents below live as `agents/*.md` files and are dispatched by skills:

- `pr-reviewer` — unified PR reviewer — handles both own-work (self relation) and cross-review (cross relation) via `REVIEW_RELATION` set at Step 0.5. The pipeline is identical in both relations — same findings, same gates, same verdict — and only the framing differs: self mode drops the context-asymmetry hedging for direct phrasing, cross mode keeps it. Read-only in both: it never auto-fixes (auto-fix lives in `implement-suggestion` and `code-quality simplify`). **Six-phase detection core** — the pipeline that decides *what to look at, how hard, and what survives*, each phase owning one rule file under `agents/pr-reviewer/rules/`: **Phase A** materializes the workspace ([`workspace.md`](./agents/pr-reviewer/rules/workspace.md)) and binds `DEPTH_CAPABILITY` ∈ `checkout` / `tarball` / `diff-only` — a review that could not read the code around the diff says so instead of reviewing the diff as if it were the program. `checkout` is reached by a **rung 0** worktree over the **local object store** whenever the cwd is a clone of the PR's repo — no network clone, and **full** history rather than 50 commits. The rung is about the local clone, not a tool: [`gw checkout --no-hooks <PR>`](https://github.com/mthines/gw-tools) is preferred for its stable discoverable path and reuse, and plain `git worktree add --detach <path> $HEAD_SHA` is the fallback, so a missing `gw` costs the rung nothing (`gw` selects the implementation, it never gates the rung); the precondition is instead the clone plus a fetch of **`pull/<n>/head`**, since a fork PR's head branch is absent from `origin` and branch-fetching would silently restrict rung 0 to same-repo PRs. `--no-hooks` is mandatory in every relation because a review reads code rather than building it, and a hook running `pnpm install` would both contradict `workspace.install: false` and execute a fork's install scripts through a path the pipeline never chose; the plain-git path runs nothing and needs no such rule. Rung 0 also makes disposal load-bearing, so `WORKDIR_CLEANUP` is a three-valued enum (`none` / `worktree` / `rm`) rather than an owned/not-owned boolean: `rm -rf` is correct **only** for a temp clone or tarball, a `gw` worktree is never removed at all (its output cannot distinguish a just-created worktree from one open for a week), and a plain-git worktree goes through `git worktree remove` — because `rm -rf` on *either* kind leaves a stale entry in the parent repo's `.git/worktrees`, so the review breaks the repo it was reviewing while deleting only its own scratch directory (guarded by L1 `G38g`, each check probed by breaking it); **Phase B** builds `impact.json` ([`impact-graph.md`](./agents/pr-reviewer/rules/impact-graph.md), `scripts/build-impact-graph.mjs`) — changed exports, their consumers, `blast_radius.band`, lockfile-resolved `dependencies[].semver_delta` with `usage_sites[]`, and `overlaps[]`; **Phase C** routes depth ([`depth-routing.md`](./agents/pr-reviewer/rules/depth-routing.md)) on what the change *reaches* rather than how big it is; **Phase D** runs independent finders ([`finders.md`](./agents/pr-reviewer/rules/finders.md), plus [`finder-consumer-impact.md`](./agents/pr-reviewer/rules/finder-consumer-impact.md) and [`finder-dependency.md`](./agents/pr-reviewer/rules/finder-dependency.md)) under one polarity rule — **finders flag, the verifier filters**, so a finder that self-censors costs a finding nothing downstream can recover; **Phase E** verifies every candidate ([`finding-verifier.md`](./agents/shared/rules/finding-verifier.md)) on Reproducible 40 / Attributable 30 / Actionable 30 with four verdicts (`confirmed` / `contradicted` / `ambiguous` / `unobtainable`, the last distinct from a `null` receipt and capped below `issue:`); **Phase F** is the comment shape the survivors are written in ([`comment-shape.md`](./agents/shared/rules/comment-shape.md)). **One report comment + inline findings (Step 4):** the report body lives in one PR issue comment per PR, rewritten in place every run and carrying **nothing machine-private**; inline findings stay **append-only** on a visible `COMMENT` review, posted at Step 4b under **exactly one condition — the run has new inline findings**. A review object exists only to carry comments at the code, so a converging `review-loop` leaves one edited report and no timeline noise. The three retired conditions (first run, verdict worsened `PASS<WARN<FAIL`, new blocking fingerprint) were notification devices that posted a review with an empty `comments` array; the accepted cost of dropping them is stated in Step 4b — a verdict that worsens with zero inline findings now updates the report silently, and re-adding it is one condition plus one renderer form. **Run state is a LoreKit state record, not a comment block (Step 0.7 + 4c):** one record per PR — tag `ci::pr-review-state`, key `ci-state::pr-review-<n>`, scope `branch::{owner}/{repo}::{head}`, `kind: bus`, `host: reviewer`, 7-day TTL refreshed on every write — holding the delta baseline, the run-mode history the deep-lens refresh counts, the open-thread set, and the deferred + anchorless findings a re-review carries forward, all **structured**. It replaced a `<!-- PR_REVIEWER_LEDGER -->` block in the report body plus a Markdown re-parse of the agent's own accordion, which coupled the reviewer's memory to its own presentation (a heading rename cost a re-review its carried findings) and forced a whole degraded-ledger sub-system — a truncated copy smuggled onto an append-only review body through a three-rung reduction ladder against a 1500-char budget — because state had to ride on the object that had just failed to write. Now the three writes fail independently: a run that cannot patch the sticky still records its state, so nothing is lost. On a miss or an unreadable record, **one** GitHub rung recovers the delta baseline from the sticky's footer SHA (marker-keyed, never login-keyed) and announces that carry-forward is empty; the retired legacy-report and pointer-ledger fetch ladders are gone. `branch::` scope keeps per-PR state out of the `repo::` scope an agent's SessionStart injection reads, and the record self-cleans on TTL — a LoreKit-side GitHub-integration purge on `pull_request: closed (merged)` is the intended accelerant and is **not yet shipped**. The agent cannot delete a memory: `mcp__lorekit__memory_delete` is deliberately absent from its `tools:` grant. **Both output surfaces are renderer-owned, and they share one vocabulary.** The report had a fail-closed renderer and the inline findings had a prose rule plus a `passes_shape()` function nothing executed — so the report's contract held and the inline one eroded, which is why the two surfaces came to share no visual system at all (no common footer, glyphs on the report only, a title on neither, and a posted finding on `dash0hq/dash0#18362` that dropped three documented decorations at once). [`render-comment.mjs`](./agents/pr-reviewer/scripts/render-comment.mjs) is the inline counterpart to `render-report.mjs`: one JSON payload per finding (`{PREFIX, TIER, TITLE, BODY, BLOCKING, EVIDENCE[]|UNVERIFIED, FENCE, FP, FIX_URL, SHA}`) in, one comment body out, fail-closed on an unknown key or a violated cap, with committed reference renderings in `scripts/eval/fixtures/inline-comment/` diffed by L1 (`G46`). Both renderers import [`comment-spine.mjs`](./agents/pr-reviewer/scripts/comment-spine.mjs) — the tier glyph map, the attribution footer builder, the theme-aware button markup, and the caps — and that single import is the mechanism: a change to the vocabulary cannot land on one surface only (`G46f` asserts neither renderer holds a local copy). **One asymmetry, stated as a rule:** a `###` heading means the report, a bold title means one finding; each renderer's post-conditions enforce its own half. On the inline surface a claim (`issue:` / `suggestion:`) now opens `issue (high): 🟠 **<≤ 60-char noun phrase>** **(blocking)**` — the prefix, tier label and colon keep position 0 so `record-comment-relevance.mjs`'s `SEVERITY_RE` reads the tier unchanged, and the title exists because GitHub shows only a comment's opening in the Files rail, the timeline and the notification email; a one-liner (`nitpick:` / `question:` / `praise:`) stays one line, and the renderer rejects a title on one and requires it on the other. Prose drops to 200 chars to pay for the title, and every posted comment carries the shared footer's **identity half** — `<sup>`pr-reviewer` · commit `<sha7>`</sup>`, byte-identical to the report's opening — the cue that makes an inline finding and the report recognisably the same reviewer, and the only attribution visible in an email. Only the identity half: the `[how these findings are produced]` methodology link is **report-only**, because repeating it under twenty inline findings spends a line per comment restating what the report says once, on the surface with the least room for it. The shared builder is the same function; the arguments differ, as they already did for the report's run line and `updated` stamp, and `footerLine()`'s `docs` flag defaults **off** so a surface has to *ask* for the link and the inline one cannot silently regain it (`G46e` asserts its absence on the four inline reference renderings; `G25`'s byte-diff pins its presence on the report's). On the report, `HEADLINE` is gone: it was the most-read line in the system and the only slot checked merely for non-emptiness, which is how `Not ready — this PR adds github.check_run…` shipped against a spec defining three fixed forms. `VERDICT` + `FINDINGS[]` + `SUMMARY` replace it, and the renderer derives the count-forward heading (`### 🟠 4 findings — 1 blocking`), a **visible findings index** above the accordions (one linked row per inline finding, carrying the same `title` — the worklist the report never had, and why an inline finding no longer needs to cross-reference the report), the `Severity — 🟠 1 high` tally (glyph paired with its word, WCAG 1.4.1), and the shared footer below the accordion. Two contradictions became unrepresentable: a `VERDICT` disagreeing with its own gate table (the `reviewer-lessons` "gate table says PASS while contract says FAIL" case, CI counted as a warning gate that can raise the verdict to WARN and never past it), and a `FINDINGS` length disagreeing with `QUALITY`'s `posted inline <N>` — the report's index and its own tally are one number stated twice. The accordion summaries lost their pipeline vocabulary (`cleared review, not inlined` → `<N> more findings — verified, too minor to comment on`; `Low-confidence findings` → `Less certain`), and the **Fix-with-Agent0 buttons are on by default everywhere** — a repo opts out with `agent0_fix_links: false` in its review config, or `--no-fix-links` for one run, and `agent0_environment` now picks the host only rather than gating whether they render (the prior default required naming an environment, which just moved the forgetting one level up) — joined by the optional `agent0_org`, a third independent key that appends `&org=<slug>` so a reader belonging to several Dash0 organizations opens the intended one, absent by default (no `org` parameter at all, which is the correct link for anyone with exactly one org), validated against `^[A-Za-z0-9][A-Za-z0-9._-]{0,62}$` at both the shell and the script so a typo resolves to no org rather than reaching the query string unencoded, and threaded to both button sites as `--org` exactly as `--env` is (L1 `G31j`–`G31m`, `G32q`, `G37c`); one flag governs both placements, so the *flag* can never render *Fix all* above findings with no *Fix this*, rendered from theme-aware 36 px assets via `<picture>` — up from a 28 px dark-only chip that was the primary CTA of the review and ignored the reader's theme. Each button's deep link is **one `/pr-fix` call plus an address** — the PR, whose comments, and (for *Fix this*) the one `path:line` to scope to — never the method: the embedded `gh api graphql` worklist query, the `{lead}` excerpt, and the `{count}` checksum were all retired into Agent0's own `/pr-fix` skill, taking *Fix all* from ~1100 encoded chars to ~190 (flat in the finding count) and *Fix this* from ~880 to ~360, with `G32k` holding both under a 500-char regression bound so a re-added clause reads as a regression instead of vanishing into headroom. Two consequences are load-bearing: the author is **always named, never left to `/pr-fix`'s own resolution** — either as the `<author>` argument (`/pr-fix` excludes bot authors unless one is named, so an omitted login would silently skip every finding of a reviewer posting as a bot, and it is also what keeps the run off every other author's comments) or, when the identity ladder resolves nothing and a prior sticky was matched, by passing that sticky's own `#issuecomment-<id>` permalink as the `<pr>` slot so the comment it names resolves the author with no `<author>` argument at all; and because the prompt no longer quotes a body, the link is stable across a prose trim. `/pr-fix`'s argument grammar, its single-author default, and its verification behaviour are asserted here but **not verifiable from this repo** — the templates are correct only if those hold, and the delegated-verification dependency (repo's own scripts, never a raw `tsc`/`eslint`, never a whole-repo pass) is stated in the rule file so it stays auditable.

The report body is **not hand-written**: layout lives in one template (`agents/pr-reviewer/templates/report-body.md`) and is filled by one script (`agents/pr-reviewer/scripts/render-report.mjs`) from a **structured** JSON payload the run supplies — counts are derived from array length, links are built by the renderer from `{path, line, url}`, and the footer/`Run mode` lines are derived from a `RUN` object, so a count cannot disagree with its list, a link cannot arrive caged in a code span, and a sha cannot appear at two lengths in one report, so the markup is deterministic and the renderer fails closed (unknown key, missing slot, invalid gate glyph, smuggled `**Verdict**` line ⇒ non-zero exit, nothing on stdout). Committed snapshots in `scripts/eval/fixtures/report-body/*.expected.md` are the reference rendering and are diffed by L1 (G25). This replaced three ~85%-identical embedded templates that five production runs averaged into a remembered shape, dropping the marker and the accordion. The whole report — gate table, run mode, memories, quality, and the open-threads list — lives inside one **collapsed `Review details` `<details>` accordion** (never `<details open>`, never flattened to the top level), so the visible report is a headline plus at most one notice line. Inside it the run-state is **grouped, not flat**: nine `**Label** — value` lines at identical visual weight became three bold group headings — `**Needs attention**` (the gate table + open threads, rendered only when a gate is actually not ✅, and never by red CI, which is informational-in-`Run` and never a gate), `**Found**` (quality, severity, optimality, standards), and `**Run**` (the run line, an `⚠️` `RUN_ANOMALY` line, coverage, CI, memories) — with plain in-group labels beneath them, so the eye lands on the headings first. A lens with nothing to report is named once in a trailing `<sup>Nothing to report — …</sup>` footnote instead of spending a line on a value that carries no information; emptiness is read from each slot's own documented grammar, a lens renders as a line **xor** a footnote entry (L1-enforced, never both and never neither), and an unrecognised value falls back to rendering its own line — more visible, never silence. Two consequences for the parse grammar, both landed in the same commit per [`reviewer-report-ingest.md`](./agents/shared/rules/reviewer-report-ingest.md)'s own rule: the run line lost its `**Run mode**` label (the `**Run**` heading carries it) so its anchor is now its own renderer-guaranteed `<mode> · <N> lines in delta` shape, and an absent `Standards — ` / `Optimality — ` / `Skipped files — ` line means the lens was quiet, not skipped. `RUN_ANOMALY` is a new payload slot separate from `RUN_NOTE` because they are different claims — routing colour appended to the run line vs. a caveat about what the review *covered*; a compare-range-pollution notice rode at the tail of the longest line in the accordion and went unread, so the renderer now rejects a `RUN_NOTE` carrying a `⚠️`. Gate 3's open threads render across two slots: `OPEN_THREADS_SUFFIX` appends the open count (plus the blocking subset on ❌) to the accordion's own `<summary>` — visible while collapsed, and the control the reader clicks, so the gate is never silent at zero extra vertical cost — and `OPEN_THREADS_LIST` holds the per-thread bullets inside the accordion right below the gate table. The standalone notice line and the `(<N> memories used)` summary tag are both retired as restatements; memory state renders inside via `MEMORIES_SECTION`. The report is written **only** to the sticky: prior-run detection matches it by marker (never by bot login, which is unresolvable on access paths where `/user` 401s), and an access path that cannot patch an issue comment — or a caller whose own guardrails forbid the write outright, a distinct and equally-covered branch (`STICKY_WRITE_FORBIDDEN`) since an earlier version had no rule for it and improvised ad-hoc report prose instead (`mthines/lorekit#514`-`#518`) — posts a compact pointer carrying just the headline and the reason (no ledger — the state record already has the history), never a second copy of the report; a degraded run with no inline findings posts nothing and reports through the terminal instead. That pointer is itself renderer-owned, not hand-written: both forms (`pointer` / `degraded`) are built from a small JSON payload by `agents/pr-reviewer/scripts/render-pointer.mjs`, fail-closed the same way `render-report.mjs` is, and diffed against `scripts/eval/fixtures/report-pointer/*.expected.md` by L1 (G29). The retired `no_prior` and `escalation` forms served the notification-only reviews and are now *rejected* by name rather than left as unreachable branches, as is any `LEDGER` key or smuggled ledger block. `POST /issues/{n}/comments` is permitted for the sticky and nothing else; inline comments are never edited or deleted. A PR whose only report predates the sticky is treated as a first run — one full review, after which it has a record and a sticky like any other. There is no `--publish` token and no pending/draft workflow. Default-on **optimality lens** (Step 2.4c) via `optimize-approach` — **`deep` tier only** (an approach-level judgement on a delta the run cannot see whole is a guess), report-only in both relations, applied only by the separate `polish optimize` pass (`--no-optimize` opts out), routed through `agents/shared/rules/optimality-review.md`. Default-on **standards-conformance lens** (Step 2.4d, `deep` and `standard`) via `agents/shared/rules/standards-conformance.md` — enforces the repo's own governing docs (`CLAUDE.md`, `AGENTS.md`, `.claude/rules/*.md`, review-config `standards:` — default `.github/review.yaml`, legacy root `.review.yaml` still honoured) as real `issue:`/`suggestion:` findings; every finding cites the governing-doc `path:line` as grounding; skip with `--no-standards`. Default-on **measurability lens** (Step 2.4e, `deep` and `standard`) via `agents/shared/rules/measurability-review.md` — the one question no other lens asks: *will this change's impact be provable, and its regressions visible, after merge?* It delegates to `measurable audit` (never `implement` — this reviewer is read-only) behind **two** gates that are the whole reason it can be on by default: a changed path classified `web`/`mobile`/`api`/`worker`, **and** new or changed observable behaviour, so a rename, a type-only change, or a behaviour-identical refactor is a quiet no-op rather than a "where's the telemetry" comment the author is right to dismiss. `missing` → `issue:` (strict, new failure mode) / `suggestion:` (else), `unlinked` → **one** aggregated `suggestion:` (strict) / `nitpick:` (advisory) per run, `pass` → nothing at all; findings name the **signal, not the library** (absent an Observability Profile the review cannot know the repo's SDK) and verify at Tier 1, since "no emit call exists on this path" is a `grep` claim. Strict is the **default**, so a `missing` on a new failure mode reaches `FAIL_REASONS`; a repo opts **down** with `measurable: advisory` (or `--measurable-advisory`) to keep every measurability finding out of the verdict, and `unlinked` never blocks under either level (a `suggestion:` under strict, an aggregated `nitpick:` under advisory); skip with `--no-measurable`. Two-tier holistic review: broad whole-PR pass (Step 2.4) plus default-on **targeted escalation** (Step 2.4b) that fans out parallel, single-target holistic traces on context-dependent findings (cap 10, `--no-escalate` to skip). **Two axes, not one (Step 1.2 / 1.2b):** the **run mode** (`full` / `incremental` / `incremental-quick` / zero-delta) decides *what* is reviewed and is the parseable grammar field the report and [`reviewer-report-ingest.md`](./agents/shared/rules/reviewer-report-ingest.md) key on; the **depth tier** (`deep` / `standard` / `quick`) decides *how hard*, and is appended after it. Conflating them is what made a big-but-boring diff expensive and a twelve-line signature change cheap. Phase C picks the tier from five inputs — `DELTA_LINES`/`NEW_FILES`, the shape classification, `blast_radius.band` + `semver_delta`, `THREAD_OVERLAP` (the Step 2.9c thread predicate, reused), and `traffic_band` — first-match-wins, behind two pre-table rules: a **`quick` override** (`THREAD_OVERLAP ≥ 0.8` **and** `band == none` — a push answering the review re-reads nothing) and a **size exclusion** (docs-only/test-only/generated reaching nothing skips both size triggers — "excused from size, not from review", the row that otherwise routed a 340-line generated-client refresh to `deep` on line count alone). Three things the rule file now says outright, because the `shape-depth-routing` suite's misses were all readings the old layout invited: **`band == none` is not a `quick` condition** (it is one *conjunct* of the override, and most `standard` diffs reach nothing — a diff that touches no export is ordinary, not exempt from review), the `deep` **triggers are an enumerated `D1`–`D13` checklist placed *before* the tier table** with the cell reduced to `ANY of D1–D13 above`, and the worked examples cover **all three** tiers plus a `deep`-via-refresh and a `deep`-via-new-file case, where they previously showed only the extremes. The checklist is the shape lesson, not a cosmetic one: the `deep` row is both the first read and by far the longest, and thirteen `·`-separated conditions in one cell get scanned until something matches and then abandoned — so the triggers at the far end were exactly the ones misrouted (`NEW_FILES > 0`, last of the thirteen, and the *absence* of a prior `deep` pass, nested a level down inside the refresh clause). Clarifying one clause **inside** such a cell makes every later clause harder to reach: the edit that fixed the refresh grammar took the suite from one miss to two, and only lifting the conditions out fixed both. `D4`–`D6` are the refresh counters (`CUM_DELTA_LINES > FULL_REFRESH_DELTA` 150 · `INCR_RUNS_SINCE_FULL ≥ FULL_REFRESH_RUNS` 3 · no prior `deep` pass recorded) and are three **independent** triggers — a recorded prior `deep` pass satisfies neither of the other two, and its absence is `D6` firing alone; `D12`/`D13` are the two size triggers and the only two the size exclusion waives. `render-report.mjs` enforces `TIER_FOR_MODE`, so a report cannot claim a deep review while rendering an incremental mode. `DEPTH_CAPABILITY` is orthogonal and **caps** the tier: `diff-only` caps at `standard`, because a `deep` tier whose deep lenses cannot run is a label on a review that did not happen. The shape classifier (`agents/pr-reviewer/scripts/classify-shape.mjs`, self-tested by L1 `G33`) still types every diff — auth / payments / schema-migration / concurrency / api-contract / infra / secrets / propagation / dependency-bump / test-only / docs-only — and owns the high-stakes path list (repo-extensible via review-config `high_stakes_paths:`); it now feeds Phase C as one input among five rather than deciding depth by itself. `--effort high` (or `effort:` in review-config) forces `deep`, enables Tier-2/3 receipts, and raises the diversify-then-vote finder count from 3 to 5; `--full` remains an alias for forcing `deep` only. The routing table is regression-tested by the `shape-depth-routing` L2 suite, whose 22 records read the live rule file. Delta triage never trusts `compare/<prior>...<head>` blind: a divergence pre-check (summary fields first) routes rebased / force-pushed / merge-commit heads to a blob-SHA authored delta, and a zero authored delta downgrades cost but never predicts a clean pass. Imports shared rules: `finding-verifier.md` (Phase E, 2.6b — owns the score's *source*; `per-comment-confidence.md` stays the threshold/defer/severity authority), `verification-receipt.md` (the Tier 1–3 evidence ladder the verifier's Reproducible axis reads), `outcome-learning.md` (promotion loop; never per-review), `review-outcomes.md` (shared bus), `review-config.md` (review-config profile / filters / `standards:` schema; default `.github/review.yaml`, legacy root `.review.yaml` honoured), `prior-comment-awareness.md` (dedup + anti-flip-flop when PR exists), `standards-conformance.md` (default-on governing-docs enforcement, Step 1.7b discovery + Step 2.4d lens, `--no-standards`), and `comment-relevance-memory.md` (per-repo LoreKit relevance signal; reads at Step 0.7 / Step 1.0). **Memory answers one question — what does this repository already know about the code this diff touches** ([`agents/pr-reviewer/rules/memory.md`](./agents/pr-reviewer/rules/memory.md)) — and that framing is why the keys are **structural**, not prose: `fp = <finder>:<defect-class>:<symbol>@<path>` at `fp_v: 2`, built only by `agents/pr-reviewer/scripts/fingerprint.mjs` (which the webhook recorder imports rather than re-deriving, so the read and write paths cannot fork into two key spaces the way the prose-keyed v1 space did). A memory keyed by branch dies with the branch and one keyed by comment prose re-keys on every re-phrasing; `symbol@path` survives both and is available to **the next author who touches that symbol**. Four records: **symbol knowledge** (`knowledge::<symbol>@<path>`, `repo::`, 90 d — contracts, invariants, consumer counts, each with `verified_at_sha` plus a capped `history[]`), **hotspot** (`hotspot::<path>`, `repo::`, 90 d — `confirmed`/`missed`/`regressed` counters), **relevance rule** (`rule::<fp>`, `repo::`, 60 d — the *only* record that can suppress), and the `branch::`-scoped PR state above. The **Step 1.0 lesson read is keyed by tag and scope, and by nothing else** — stated explicitly in the agent body after the `code-review-retrieval-relevance` suite's misses turned out to be two non-filters the old wording only implied by absence: it is **not filtered by the diff** (diff relevance governs the Step 1.2c *search*, which is an OR on top of the list read and never a filter over it), and it is **not gated on `seen_count`** (≥ 3 is the *promotion* bar in `outcome-learning.md`, never a surfacing threshold). What does exclude a record is named alongside them — the wrong loop namespace, the wrong scope, or falling outside the `limit: 50` window. The knowledge reads happen **after Phase B**, keyed by the impact graph rather than by paging the whole scope, and every read filters on `source.agent`: another bot's declined finding and a human's incidental comment are counted as hotspot signal but **never train this agent's suppressor**, since each has its own bar and its own false-positive profile. A knowledge fact is **re-verified or dropped, never trusted** — memory accelerates verification, it never substitutes for it, so a memory-grounded finding still carries its own receipt. **Suppression is applied at Step 2.7b, after Phase E verification, never at find time**: suppressing before verification drops a candidate nobody looked at on the strength of a fingerprint match, while suppressing after it drops a *verified* finding the repo has repeatedly declined, which is a recordable maintainer preference — and two classes are never suppressible at all (a `standards` finding, because the repo's own written rule outranks its reviewers' fatigue, and any `(blocking)` finding, where the rule match is surfaced as evidence instead of applied). Lifecycle (`candidate`/`active`/`disabled`) is **recomputed at read time** from `evidence[]`, needing ≥ 3 concordant signals from **≥ 2 distinct PRs** — one author having a bad day is not a repository preference — which also makes a lost read-modify-write race harmless. `/pr-review remember <fact>` lets a maintainer write an `active` rule with no corroboration threshold, and cannot `remember` away either never-suppressible class. `reviewer-lessons` stay advisory and are still **never written in-run** (all writes flow through `outcome-learning.md` post-merge), with two additions: a matched lesson contradicted by an `active suppress` rule is handed to the finders **with the contradiction stated** rather than silently dropped, and a lesson about a missed or false finding is tagged `detection::<finder>` so each promotion becomes a seeded case in the `bug-detection` eval suite. **Telemetry is an exposure input, never a verdict** ([`telemetry.md`](./agents/pr-reviewer/rules/telemetry.md)): no telemetry exists for the change before merge, so Dash0 data feeds `traffic_band` and error-signature history under three invariants — it **raises** priority and never lowers it, it **never blocks** (no telemetry term ever reaches `FAIL_REASONS`), and it reads **aggregates and signatures only**. On a re-review (second+ pass) it runs `thread-resolution.md` at **Step 2.9c — before the verdict and before posting** (moved from the old post-posting Step 4.5): auto-resolves its own addressed/declined threads, removes the successfully-resolved ones from `OPEN_BOT_COMMENTS[]`, re-evaluates Gate 3 against the updated set, and writes to `reviewer-comment-relevance`. Running it after posting published an unblock checklist naming threads the same run closed seconds later. The checklist itself renders as plain bullets (never `- [ ]` task-list checkboxes, which are human-clickable and would contradict the `isResolved` authority) with resolved entries **removed** rather than ticked, plus a `<R> resolved since <sha>` progress counter. **Gate 2 (CI) is informational-in-`Run`, it never grades and never fails** — red or pending CI renders ⚠️ in its own reported state but is excluded from `WARN_GATE_COUNT`, contributes no token to `SEVERITY_TALLY`, and no phrase to `FAIL_REASONS` or `WARN_REASONS`; its substance is reported in `CI_NOTE` alone, so a PR with a clean review and a red or pending check still renders the clean PASS headline. The agent did not diagnose the failure and cannot separate a real regression from a flaky job, an infrastructure quota, a check that does not run on this base branch, or a draft with no workflow wired up, and GitHub already blocks the merge on a required check; `mthines/lorekit#490` led with `CI failing, 1 error, 2 warnings … Blocking: CI checks failing`, reporting the reviewer as having found something blocking when it had not. A red check the diff demonstrably causes is a Gate 6 finding instead, on this reviewer's own evidence (`F-ci-failed-the-verdict`, guarded by L1 `G27`). **Gate 3 (`Prior review feedback`) is tri-state**, on the same blocking bar as Gate 6, and tracks every open review thread — bot **or** human — labelling each in the report by author type (`(bot · \`login\`)` / `(human · \`login\`)`) rather than calling them all "bot threads": ❌ only when an open thread's ask carries the authoring bot's own blocking decoration (`(blocking)` / `issue:` / an explicit severity label — never re-adjudicated by re-reading the code) **and** `answered == false` (no reply on the thread); otherwise ⚠️, which never flips the verdict. That is what stops a `nitpick:` nobody clicked Resolve on, a suggestion declined on-thread with a rationale, or a finding already fixed in a later commit from failing a PR that has nothing left to fix — the same principle as the existing *an unknown thread never fails it* rule. Both non-passing states render the full `OPEN_THREADS_LIST` (only the summary suffix differs — ` (<K> blocking)` is appended on ❌ and dropped entirely on ⚠️, never `(0 blocking)`), so softening the verdict never shrinks the worklist. **Thoroughness levers (so a weak PR gets everything it deserves, not a trickle across re-reviews):** (1) **deep-lens refresh** — an incremental re-review is promoted back to `deep` when cumulative churn since the last `deep` pass exceeds `FULL_REFRESH_DELTA` (150 lines), when `INCR_RUNS_SINCE_FULL` reaches `FULL_REFRESH_RUNS` (3), or when no prior `deep` pass is recorded — which includes every run on the fallback rung, since it recovers a baseline but no history — so the holistic passes (2.4/2.4b) never stay skipped forever (Step 0.7 reads `LAST_FULL_SHA` off the record; Step 1.2b upgrades); (2) **confidence defer, not drop** — a near-miss `issue`/`suggestion` (Final in `[max(threshold−15, 50), threshold)`) is deferred to a `Low-confidence findings` advisory body section (`CADV`) instead of being silently dropped — advisory-only, never inline, never auto-applied (`reviewer-report-ingest.md`), never in the `cleared − deferred = posted` identity; (3) **blocking findings are cap-exempt** — a `(blocking)` finding always posts inline and is never deferred, so the per-file/20-total caps govern non-blocking overflow only (`rubric-composition.md § Placement`); (4) **optimality inline pointer** — a proposal with `analysis_confidence ≥ 95` and a resolvable anchor also leaves one short inline `suggestion:` pointer to its body card (`optimality-review.md § Inline pointer`). **Finders replace personas.** The pipeline that asked *one* careful generator to raise findings and then ran eleven filters over its output had the polarity backwards — a careful generator does the filters' job badly and in secret, and nothing downstream can distinguish "no defect there" from "the generator talked itself out of it". Six finders (`correctness`, `consumer-impact`, `dependency`, `intent`, `standards`, `quality`) now emit candidate records independently and know nothing about thresholds, caps, or suppression; Phase E decides what survives. Personas 1–3 are folded into `correctness` / `quality` / `intent`, and **Persona 4 is retired** into `finder-dependency.md`, which does the thing the persona never did: resolves the version from the **lockfile** (never the manifest, and a `0.x` minor is `major` with `zerover: true`), walks a five-rung changelog ladder for the whole range `(from, to]`, intersects each documented break with `usage_sites[]`, and anchors the finding at the **usage site rather than the lockfile** — with exactly three outcomes and never a silent fourth (an `issue` at a usage site, a one-line "6 sites checked, none affected" report note, or a **withheld hypothesis** naming the sites it would have checked, labelled `unverified (upstream unreachable)` and never an `issue`). Its cross-owner-401 rule is load-bearing: the injected `gh` credential is scoped to this PR's own repository, so a 401 reading an upstream's releases is **scoping, not breakage** — pivot to anonymous HTTP, never retry the `gh` call, never report it as unverifiable. **Output surfaces:** the posted body is renderer-owned as before, and the Step 3 **terminal** template — which has no renderer and where a second copy would be the drift — now lives as the one copy in [`terminal-report.md`](./agents/pr-reviewer/rules/terminal-report.md), with the agent body reduced to a router. [`line-validity.md`](./agents/pr-reviewer/rules/line-validity.md) still owns the pure in-memory RIGHT-side hunk-bounds pre-flight, and [`diagnostic-surface.md`](./agents/pr-reviewer/rules/diagnostic-surface.md) is the `diagnose` entry point, updated to the phase model. Research basis: [`references/detection-research.md`](./agents/pr-reviewer/references/detection-research.md) — what each borrowed principle came from (finder/verifier separation and aggressive finders from Claude Code Review and Cursor's own report that its agentic rebuild *under*-flagged until told to err on the side of flagging; diversify-then-vote, effort tiers, incremental-by-default, and candidate → promote → auto-disable learned rules from Bugbot; addressed-between-commits as an outcome signal from Greptile), the three deliberate departures (a resolved consumer graph rather than similarity search, since a best-effort search cannot be a routing input; dependency reasoning derived from first principles because no reviewer documents any; structural `symbol@path` keys rather than per-repo prose keys), and why no published precision figure is a target here — the numbers disagree by a factor of two and every recall-only benchmark is blind to the failure mode `l2-detection.mjs` gates on by pairing `recall ≥ 0.7` with `fp ≤ 0.2`.

### Markdown artifact click-open model

All markdown artifact rows in both trees (Agent Tasks `agentTasksExplorer` and Sessions `agentSessionsExplorer`) use a single-vs-double-click debounce routed through the shared `agentTasks.openMarkdown` command:

- **Single click** → opens the rendered markdown preview (`markdown.showPreview`).
  The action fires after a 300 ms window with no second click, so a double click never flashes the preview.
- **Double click** → opens a persistent, editable editor tab (`vscode.window.showTextDocument` with `{ preview: false }`).
  Triggered when a second click on the same path arrives within 300 ms of the first.

This applies to plan, task, walkthrough, diagnose, and other-markdown rows.
The 300 ms double-click window is `DOUBLE_CLICK_MS` in `src/lib/markdown-click-handler.ts`.

The `ArtifactWatcher.openArtifact` programmatic auto-open path (triggered when a new artifact is generated by an agent) always opens an editable editor directly — it does not route through the click debounce.

The deprecated `agentTasks.openMarkdownInPreview` setting remains a no-op; the click model above supersedes it.

### Sessions panel — status model

The Sessions panel uses a four-tier status computation:

1. Terminal open in this window → `running` (definite signal).
2. Hook override within 5-minute TTL → hook-driven status.
3. Unread TTL (24h): if hook override is `unread` and `session.mtime > 24h`, downgrade to `idle`.
4. We closed the terminal post-mtime → `idle` (we ended it).
5. Fallback → `deriveRunState(turnEnded, mtime)` from JSONL.

Status values: `running` | `needs-input` | `unread` | `stalled` | `idle`.
Plus PR-derived display-only statuses: `pr-open` | `pr-ci-failing` | `pr-merged` | `pr-closed`.

`unread` is set when a `Stop` hook fires and the session's terminal is NOT open.
`needs-input` is set when a `Stop` hook fires and the terminal IS open.
`unread` clears when the user opens the session (`clearUnread` is called in `openSession`).

**Duplicate-Stop guard**: `clearUnread` records a timestamp; subsequent `Stop` events with an older `ts` are discarded so a duplicate hook call cannot re-set the `unread` badge after the user dismissed it.

**Sessions from deleted worktrees**: silently vanish from the panel on the next refresh.
`~/.claude/projects/` entries for deleted worktrees are not garbage-collected by this extension — Claude Code manages its own project dirs.

### PR linkage

PR status is fetched via `gh pr view --head <branch>` at a 90-second cadence by `PrPoller`.
Requires the `gh` CLI.
Controlled by `agentTasks.sessions.prLinkage` (boolean, default `true`).
When `prLinkage = false`, no `gh` subprocess calls are made.
When `gh` is not installed, a one-time info notification fires and all sessions show JSONL-derived status.
`PrStatusCache` implements the no-flip guarantee: a `pr-merged` cache entry is never overwritten by a transient `gh` error.
PR polling is capped at 20 most-recently-active branches (by mtime) to stay well within GitHub's 5000 req/hour limit.

## Local Development

The author's machine wires this repo into Claude Code via a two-tier symlink chain so every edit to `skills/<category>/<name>/SKILL.md` is picked up live on the next turn — no `npx skills add` reinstall.

```
~/.claude/skills/<name>     →  ~/.agents/skills/<name>     →  <this repo>/skills/<category>/<name>
~/.claude/agents/<name>.md  →  ~/.agents/agents/<name>.md  →  <this repo>/agents/<name>.md
```

The installed-side paths stay flat (`~/.claude/skills/<name>`, `~/.agents/skills/<name>`) because that's how every Agent-Skills-compatible tool reads them. Only the repo target is nested — the sync script walks `skills/` recursively to find every directory with a `SKILL.md`.

The middle layer (`~/.agents/skills/`) is the cross-tool discovery directory used by Codex, Cursor, OpenCode, and other Agent Skills-compatible clients, so a single chain serves every tool.

### Add a new skill

1. Pick a category (`workflow/`, `quality/`, `delivery/`, `testing/`, `design/`, `analysis/`, `authoring/`) and create `skills/<category>/<name>/SKILL.md`.
2. Run `bash scripts/sync-symlinks.sh` to wire up the two-tier chain for every new or missing skill/agent in one pass.
3. Add an entry to the inventory in `CLAUDE.md` and `README.md`.

For agents, write `agents/<name>.md` in this repo and rerun `bash scripts/sync-symlinks.sh`.

Skill-local installers: if a skill ships `skills/<category>/<name>/install.sh`, `sync-symlinks.sh` discovers it and runs `bash <path> --development --quiet` after the main symlink pass. The installer must accept both flags, be idempotent, and write errors to stderr. See `skills/workflow/autonomous-workflow/install.sh` for the reference implementation.

Naming files a skill installs by symlink: when a skill's `install.sh` symlinks a file *verbatim* into `~/.claude/agents/` or `~/.claude/rules/` (as `autonomous-workflow` does from its `templates/` directory), name the source after what it *is* — `<agent-name>.agent.md` for an agent (e.g. `aw-planner.agent.md` → installed as `aw-planner.md`) and `<name>.rule.md` for a rule (e.g. `routing.rule.md`) — not `*.template.md`. These are definitions, not fill-in templates (no substitution happens), and the `<name>.agent.md` form lets a repo search for the agent name land directly on the file. Reserve `*.template.md` / plain `templates/*.md` for boilerplate a skill *emits or fills in* at runtime (e.g. `aw-create-plan`'s `plan.md`).

Invoke the script with `bash` (or `./scripts/sync-symlinks.sh`), **not** `sh` — the script uses bash arrays and process substitution, which POSIX sh doesn't support.

The script is idempotent: it skips entries that are already linked correctly, repairs broken or wrong-target symlinks, and refuses to overwrite real files or directories. Pass `--dry-run` (or `-n`) to preview without applying.

### Edit an existing skill

Edit the file at `skills/<category>/<name>/SKILL.md` in this repo directly — never through the `~/.claude` or `~/.agents` symlinked path. Writes through symlinks resolve correctly but make it ambiguous which checkout the change lands in, which matters when multiple worktrees exist.

### Verify a skill is wired up

```bash
readlink ~/.claude/skills/<name>     # → ~/.agents/skills/<name>
readlink ~/.agents/skills/<name>     # → <repo>/skills/<category>/<name>
readlink ~/.claude/agents/<name>.md  # → ~/.agents/agents/<name>.md   (agents only)
readlink ~/.agents/agents/<name>.md  # → <repo>/agents/<name>.md      (agents only)
```

All applicable hops must resolve. If any is missing, the harness will not see the skill or agent.

- **L2 — behavioral evals** (`ANTHROPIC_API_KEY=… node scripts/eval/l2.mjs`): data-driven runner, one suite per labelled decision — `tier-routing`, `bug-class`, `complexity-triage`, `aw-should-trigger`, `reviewer-agreement-bump`, `optimize-approach-optimality`, `severity-tiering`, `shape-depth-routing` (pr-reviewer Phase C: `deep` vs. `standard` vs. `quick`, 22 records read against the live [`depth-routing.md`](./agents/pr-reviewer/rules/depth-routing.md) — the file that owns the decision, including its two pre-table rules), `code-review-retrieval-relevance` (golden sets in `scripts/eval/golden/`). Each reads the skill's live rubric section and exact-matches the model's choice — through `rubric.section` (one slice, or the whole file) or `rubric.sections` (an ordered list, for a decision whose owning prose is split across sibling subsections), resolved by the fail-closed `rubricFor()`: an empty list, both keys set, or a rubric shape neither of `G21g`'s two parses recognises is an error, never an empty prompt. **A rubric broader than the question is a defect, not padding.** In CI via [`.github/workflows/evals-l2.yml`](./.github/workflows/evals-l2.yml) — **opt-in, because every case is a model call**: suites run only on an explicit ask (the `run-evals` PR label, or a `workflow_dispatch` whose `suites` input takes `all` or a name list), so an unlabelled PR pays one ~3s bookkeeping job with no checkout and no API call. The `pull_request` trigger deliberately stays: the trigger governs whether the CHECK appears, the gate governs whether SUITES RUN, and a `workflow_dispatch`-only workflow never reports on a PR, so requiring its check would leave every PR pending forever — the same trap the old `paths:` filter set. `G21i` asserts both halves (the suite jobs are reachable only through the opt-in; the aggregator is `if: always()` and the `pull_request` trigger is present) plus that the label name the workflow reads is the one the README documents. It needs an `ANTHROPIC_API_KEY` repo secret, soft-gates per suite at a 70% catastrophic floor (golden sets < 50 ⇒ report-only-ish per `evals.md`). **A suite below `EVAL_GATE_MIN_CASES` (10) cannot breach that floor** — it runs, prints its accuracy, and is labelled `[advisory]`, because under ten cases one case moves accuracy by ≥ 10 points and a 70% floor on a 5-case set allows exactly one miss; the remedy is more golden cases, never a lower floor. A missing key still skips cleanly (exit 0) for a fork or a fresh clone, **but the opt-in CI path sets `EVAL_REQUIRE_KEY=1` and fails (exit 3)**: 232 consecutive runs were green because the secret was unset, and a run someone explicitly asked for must not report green having measured nothing — the `::warning` step remains for the human-readable cause. **Four scorer/gate rules are guarded by `G21l`, which extracts `parseChoice` from the live runner and EXECUTES it:** a reply that enumerates every choice reads as ambiguous, never as the first one (the old earliest-substring rule scored the `MODE SELECTION:` block's own `[Micro | Lite | Full]` template line as a confident `Micro` — which is how all five `tier-routing` misses landed on one label and read as a rubric defect for a whole run); a reply naming a choice that **contains** another (`optimal` inside `suboptimal`, `promoted` inside `not-promoted`) resolves to the **longest** match rather than to neither — `named.length === 1` could never hold in the two nested-choice suites, so every reply but the byte-exact one scored as a miss, and the guard now probes the nesting in **both** directions so the contained choice stays reachable, plus the **by-design residue** it pins: for a nested pair containment is the only evidence available, so an unbracketed enumeration resolves to the *longer* choice instead of reading as ambiguous — a real trade, taken deliberately, and asserted so it cannot be "fixed" back by re-breaking the line above it; a miss prints the model's **raw reply**, since a line showing only the parsed label cannot distinguish a wrong answer from a wrong parse; and the rubric travels as a `cache_control: ephemeral` system block, byte-identical across a suite's cases, for ~80% off the input bill at no change to any answer (the run's last line reports cache reads/writes, and distinguishes the two reasons there might be none: `cache not applicable` when the prompt is under the ~1024-token minimum cacheable prefix — true of the three smallest suites, where there is nothing to discount and nothing to fix — and `cache MISSED` only when a prompt long enough to cache produced no cache activity anyway, which is the one worth investigating; Shape: `eval.run` → `eval.suite <name>` → `eval.case <id>` (CLIENT) spans, plus `eval.case.result` (Sum, delta, split by `eval.case.match`, so accuracy is a backend-side ratio), `eval.suite.accuracy`/`eval.run.accuracy` (Gauge, `%`), `eval.case.duration` (Histogram, `s`) and the upstream-semconv `gen_ai.client.token.usage` (Histogram, `{token}`, split by `gen_ai.token.type`). Four rules, all guarded by `G21k` and each probed by breaking it: **off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set** (a fork or fresh clone attempts no export); **a MISS is not a span error** — a wrong answer is the measurement, so the case span stays `UNSET` and only a transport/API failure sets `ERROR`, since conflating them makes every rubric regression look like an outage in the trace list; **an absent attribute is omitted, never a placeholder** (`unknown` is not queryable as absent); and **the flush precedes the gate exit**, so a run that trips `EVAL_GATE` still ships the trace you most want to read — asserted positionally, because a refactor that moves the exit up would lose exactly that trace. Export failure never changes the verdict: the accuracy is the product, the span is the receipt. In CI the endpoint is a repo **variable** (a hostname is not a secret) and only `DASH0_AUTH_TOKEN` is a secret; each matrix job is its own process, so an opted-in PR yields **one trace per suite** — group by the `cicd.pipeline.run.id` resource attribute.
- **L2-detection — does the reviewer actually find the bug** (`ANTHROPIC_API_KEY=… node scripts/eval/l2-detection.mjs`, `--self-test` runs offline and is executed by L1 `G39`): a **separate** runner, because the classification runner above cannot express detection. It asks a single-choice question with `max_tokens: 16` and exact-matches the answer, so the only detection question it can pose is "is there a bug here, yes or no" — and a reviewer that answers yes to everything scores 100 % recall on it. This runner replays the real two-pass pipeline per record: the finder over the diff (reading [`finders.md`](./agents/pr-reviewer/rules/finders.md) live as its system prompt), then the verifier over each candidate it returns (reading [`finding-verifier.md`](./agents/shared/rules/finding-verifier.md) live). A candidate counts as a hit only when its path matches, its line is within `LINE_TOLERANCE = 3`, **and** the verifier confirmed it — an unparseable verdict is never read as a confirmation. Gates are `recall ≥ 0.7` and `fp ≤ 0.2`, so recall and precision are measured together and neither can be bought with the other. `golden/bug-detection.jsonl` holds 50 records — 20 seeded, four each of `logic`, `consumer-break`, `dep-breaking-change`, `intent-mismatch`, and `standards`, plus **30 controls, every one a decoy** (a seeded record with the defect removed, a fix mistakable for the bug it fixes, a rule applied where it is scoped out, a break whose usage sites the same diff already updates) so the false-positive rate measures discrimination rather than diff difficulty. **The controls grew from 10 to 30 to make `fp_rate` measurable at all** — one control was 10 points against a 20-point gate, so the metric had four usable states and could not distinguish a real precision improvement from run-to-run variance; at 30 a dirty control is 3.3 points and the gate tolerates 6, asserted by the self-test as `floor(controlN × GATES.fp) >= 4`. The fix for that assertion is always MORE CONTROLS: lowering `GATES.fp` shrinks the tolerated count, so it makes the resolution worse while looking like a concession. Consequence for the recorded runs: every `fp_rate` in the five-run baseline is over a 10-control denominator and is **not comparable as a number** to a current run's. `validate()` rejects a golden file whose defect path appears in no surface the finder is shown, which is the defect that makes a recall number meaningless. A promoted `detection::<finder>` lesson becomes a seeded case here. **It now runs in CI, in its own `bug-detection` job, and gated** — it previously ran in *no workflow at all*, so only its `--self-test` executed and the scoring plumbing was guarded while the measurement had never once run. Selection rides the same derivation as the nine suites without becoming a matrix entry (it cannot ride `--suite`): `SUITES.DETECTION` in `suites.mjs` declares the runner, the two live rubric files and the golden set, `select-suites.mjs` reports one extra boolean off that declaration, and the job consumes it — a harness change selects both it and every suite (fail-open), a `finders.md` edit selects it and no suite, a suite rubric selects a suite and not it. Unlike the suites' soft `EVAL_GATE` floor it runs with `EVAL_DETECTION_GATE=1`, because the two rates *are* its contract. `G21m` asserts the chain end to end, and the last link is the load-bearing one: the `l2` aggregator is `if: always()`, so a failed dependency reaches it as a value to *read*, and an aggregator reading only `needs.suite.result` is how a red detection run reports green (`skipped` stays a pass on either job — a PR can affect one eval and not the other). **Its first five runs measured recall 75/60/70/75/90% and fp_rate 30/40/30/≤20/40%** (all over the pre-growth 10-control denominator) on the detection core as it already stood — red in four of five, and that is the eval working, not a regression the change that permitted it introduced. Findings in [the detection baseline](./scripts/eval/README.md#the-l2-detection-baseline--the-first-three-runs), and the first one is a **retraction**: run 1 appeared to show the verifier halving the finder's false positives (50% → 30%) at *zero* recall cost — `finders.md`'s flag-then-filter polarity measured rather than argued — but run 2 shows it spending 20 points of recall for 10 of precision, a NEGATIVE lift, and run 3 comes back looking like run 1 (−10 fp at −0 recall). Two of three runs show the polarity working and one shows it inverted, across a lift spread of −10 to +20 — which at 20 seeded records (one case = 5 recall points) and 10 controls (one control = 10 fp points) is the entire spread, so **the verifier's value is not established** and no single detection run may be quoted for or against it. What the runs DO establish is that the controls are where the work goes — four of five failed on `fp_rate` while recall straddles its 70% bar, and once itemised the survivors turned out to be the controls' own defects (see below) — and that repeats are needed before and after any rubric edit. What they do **not** establish is that the precision gap is *reproducible*: an earlier reading called it that on the strength of 30/40/30, and run 4 came in at or under the gate before run 5 went back to 40, so one meet in five is a flaky gate rather than a standing red. Runs 4 and 5 are a clean same-content pair (both on a diff touching neither rubric), so the spread between them is pure variance — which is the observation the control growth above answers. `intent-mismatch` is the weak class in both (1/4 then 2/4 against 3/4–4/4 elsewhere) with most misses never flagged, so that gap is finder recall rather than verifier over-filtering; and one record failed on output *shape* (the finder replied prose instead of JSON), counted as a miss and never as clean — never loosen the parse to recover it. Raising the core's precision means editing the two rubrics this eval measures, so it needs its own golden decoys and its own re-run; lowering the gate to meet the current core is the fix-to-pass forbidden everywhere else here, and is what left the eval unrun to begin with. **Runs 6 and 7, the first two on the 50-record set, both PASSED** (recall 90%/80%, fp 20%/17%, lift +13/+20) — and run 7, the first to print its surviving controls BY NAME rather than as a count, overturned the planned next step: four and a half of the five false positives were **defective fixtures**, not verifier failures. The finder was correct that a control's `shallowClone` spread primitives, that another used `Future` with no import, that a "clean" perf diff introduced module-level state and an unenforced call ordering, and that a `mockReset()` break in a test file is still a break (the record's own "it is only a devDependency" premise was wrong). Two of the four were ORIGINAL controls carrying defects invisible for the whole recorded baseline. Tuning `finding-verifier.md` against them would have taught it to reject TRUE findings while `fp_rate` went down — the same fix-to-pass one level up, and much harder to spot. So the fixtures were repaired and the rubrics were left alone; the evidence that the verifier works is in the same output, dropping 6 of 11 flagged controls, every rescue a well-formed decoy. Two rules follow: **a control asserting "this diff is clean" is a claim about the WHOLE diff, not about the one thing it probes** (four of five probed correctly and were dirty for an unrelated reason), and **`fp_rate` alone cannot tell an over-permissive verifier from a defective control set** — five runs of a bare number pointed at the rubric, one run of named survivors pointed at the fixtures, so never tune a rubric against a rate you have not itemised.

When a lesson is promoted via `diagnose`, add a golden case so the fix is locked. Methodology: [`ai-engineering/rules/evals.md`](./skills/quality/ai-engineering/rules/evals.md).

### Keeping the evals honest (mandatory on every change)

**A change that alters a decision the evals measure MUST update the evals in the SAME commit.**
An eval is not follow-up work: a rubric edited without its suite re-run is an unverified behavioural change, and a suite left pointing at a deleted rubric is a red gate on the next author's PR.

"Big change" is not the trigger — these are, and they are exhaustive.
Look up what you touched:

| You changed… | You MUST… |
| --- | --- |
| the body of a section a suite reads (any `SUITES[].rubric.file` + `section`) | run that suite (`node scripts/eval/l2.mjs --suite <name>`) and report the accuracy. Re-label or add golden cases if the decision boundary moved; a rubric edit that changes no label is the normal case, and saying so is the deliverable |
| a section HEADING a suite reads (renamed, re-levelled, moved) | update `rubric.section` — or the matching entry in `rubric.sections` — in `suites.mjs`; `extractSection` throws on a missing anchor and L1 `G21g` fails |
| the FILE a suite reads (moved, renamed, deleted) | repoint `rubric.file`, or delete the suite entry **and** its `golden/*.jsonl` together. Never leave a suite whose extraction throws |
| a HARNESS file (`HARNESS_FILES` in `suites.mjs` — `l2.mjs`, `lib.mjs`, `suites.mjs`, `select-suites.mjs`) | run **every** suite, plus `bug-detection`. That is the selector's own rule 1 and it is fail-open by design: one of these can alter any suite's answer, so the widening direction costs tokens while the narrowing direction costs coverage and reports green either way. `telemetry.mjs` is deliberately NOT one — it observes the run and cannot move a label |
| a `choices` list — a new tier, bug class, severity, verdict | add at least one golden case labelled with each new choice, and re-label the existing ones if you renamed a choice. L1 `G21j` enforces both directions |
| added a new enumerable decision an agent makes (a routing table, a tier ladder, a class taxonomy) | add a suite: `golden/<name>.jsonl` + a `SUITES` entry. Two steps, no CI wiring — selection is derived |
| deleted a skill, agent, or rule file | grep `suites.mjs` for its path first; a suite reading a deleted file fails L1, not L2 |
| a MECHANICAL contract (a `plan.md` section list, a renderer payload key, a gate glyph, a shared verbatim sentence) | that is L1's job, not L2's — add or extend an `s.check` in `l1.mjs`, and **prove it bites** by breaking the thing it guards and watching it go red |
| the eval harness's own telemetry (`telemetry.mjs`, or the `eval.*` / `gen_ai.*` attributes `l2.mjs` stamps) | extend the module's `--self-test` (it is executed by L1 `G21k`, so the OTLP encoding cannot rot unobserved) and keep the four rules intact — off by default, a miss is not a span error, an absent attribute is omitted, the flush precedes the gate exit. Renaming an attribute is a **dashboard-breaking** change: say so in the PR description |
| a finder or verifier rule (`finders.md`, `finding-verifier.md`) | add a `golden/bug-detection.jsonl` record — including a **decoy** (the same diff with the defect removed) when the change is meant to raise recall, or the false-positive rate cannot tell discrimination from difficulty. Either of these files now selects the `bug-detection` CI job, which is **hard-gated** on `recall ≥ 0.7` / `fp ≤ 0.2`, so label the PR `run-evals` (or run `node scripts/eval/l2-detection.mjs` locally) and report both rates |
| promoted a lesson via `diagnose` (`seen_count ≥ 3`) | add the golden case, as above |

**Two obligations the opt-in CI created.**
Since suites no longer run unasked, nobody else will notice a rubric you did not verify: after any first-row change, either label the PR `run-evals` or run the affected suites locally, and put the accuracy in the PR description.
And `node scripts/eval/select-suites.mjs` on your own changed files tells you which suites the first row covers — read it rather than guessing.

**Definition of done:** the diff either touches the eval surfaces above, or the PR description says in one line why none applied.
