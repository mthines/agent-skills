Regression evals for the skills live in [`scripts/eval/`](../scripts/eval/README.md), in three layers:

- **L1 — deterministic contract checks** (`node scripts/eval/l1.mjs`): no LLM, no cost, gated in CI ([`.github/workflows/evals-l1.yml`](../.github/workflows/evals-l1.yml)) on every PR. Asserts link/anchor integrity (baseline-ratcheted), the `aw` tier table ≡ `SKILL.md` Step 1, the `plan.md` Core-section contract (runs the actual `confidence` rule #2/#3 idioms — incl. the #31 regression — plus the v3.15 rule #9 requirement-coverage, rule #10 create-⇒-survey, and rule #11 checks.yaml ID-sync idioms), `diagnose` skill resolvability, lesson-scope storage, frontmatter sanity, and cross-file contract guards (the `seen_count` UPDATE sentence shared verbatim across its three owners, fast-lane plan ⊇ Core-8 sections, `/critical`'s Must-fix bucket in `implement-suggestion`, the real `confidence(code)` contract in the per-comment gate, and a forbidden-phrase list for audited contradictions). `G38` guards the detection core across eight groups — every phase rule exists **and** the agent body routes to it, the finder polarity rule appears in both the rule and the body, all four verifier verdicts are defined with `unobtainable` distinguished from a `null` receipt, suppression is ordered after verification (asserted positionally: `indexOf("2.7b") > indexOf("2.6b")`), memory keys are structural and filtered on `source.agent`, telemetry's three invariants hold with no telemetry term reaching `FAIL_REASONS`, all three tiers and all three capabilities are named by rule + body + renderer, and the two pre-table routing rules are stated in the right order. `G39` executes the detection runner's self-test, and `G50` holds the L2 cost controls the next bullet describes — the cached rubric block, the `--suite` list and its empty-selection exit, the three-way cache notice, the fail-closed selection, and the harness-file set **including its two deliberate exclusions**, since the criterion is "can this change a suite's ANSWER" and `telemetry.mjs` / `evals-l2.yml` cannot (`G50a` is retired rather than absent: executing the selector's self-test is `G21h`'s job, and two IDs asserting one contract make a red build ambiguous about which contract broke).
- **L2 — behavioral evals** (`ANTHROPIC_API_KEY=… node scripts/eval/l2.mjs`): data-driven runner, one suite per labelled decision — `tier-routing`, `bug-class`, `complexity-triage`, `aw-should-trigger`, `reviewer-agreement-bump`, `optimize-approach-optimality`, `severity-tiering`, `code-review-retrieval-relevance` (golden sets in `scripts/eval/golden/`). Each reads the skill's live rubric section and exact-matches the model's choice — through `rubric.section` (one slice, or the whole file) or `rubric.sections` (an ordered list, for a decision whose owning prose is split across sibling subsections), resolved by the fail-closed `rubricFor()`: an empty list, both keys set, or a rubric shape neither of `G21g`'s two parses recognises is an error, never an empty prompt. **A rubric broader than the question is a defect, not padding.** In CI via [`.github/workflows/evals-l2.yml`](../.github/workflows/evals-l2.yml) — **opt-in, because every case is a model call**: suites run only on an explicit ask (the `run-evals` PR label, or a `workflow_dispatch` whose `suites` input takes `all` or a name list), so an unlabelled PR pays one ~3s bookkeeping job with no checkout and no API call. The `pull_request` trigger deliberately stays: the trigger governs whether the CHECK appears, the gate governs whether SUITES RUN, and a `workflow_dispatch`-only workflow never reports on a PR, so requiring its check would leave every PR pending forever — the same trap the old `paths:` filter set. `G21i` asserts both halves (the suite jobs are reachable only through the opt-in; the aggregator is `if: always()` and the `pull_request` trigger is present) plus that the label name the workflow reads is the one the README documents. It needs an `ANTHROPIC_API_KEY` repo secret, soft-gates per suite at a 70% catastrophic floor (golden sets < 50 ⇒ report-only-ish per `evals.md`). **A suite below `EVAL_GATE_MIN_CASES` (10) cannot breach that floor** — it runs, prints its accuracy, and is labelled `[advisory]`, because under ten cases one case moves accuracy by ≥ 10 points and a 70% floor on a 5-case set allows exactly one miss; the remedy is more golden cases, never a lower floor. A missing key still skips cleanly (exit 0) for a fork or a fresh clone, **but the opt-in CI path sets `EVAL_REQUIRE_KEY=1` and fails (exit 3)**: 232 consecutive runs were green because the secret was unset, and a run someone explicitly asked for must not report green having measured nothing — the `::warning` step remains for the human-readable cause. **Four scorer/gate rules are guarded by `G21l`, which extracts `parseChoice` from the live runner and EXECUTES it:** a reply that enumerates every choice reads as ambiguous, never as the first one (the old earliest-substring rule scored the `MODE SELECTION:` block's own `[Micro | Lite | Full]` template line as a confident `Micro` — which is how all five `tier-routing` misses landed on one label and read as a rubric defect for a whole run); a reply naming a choice that **contains** another (`optimal` inside `suboptimal`, `promoted` inside `not-promoted`) resolves to the **longest** match rather than to neither — `named.length === 1` could never hold in the two nested-choice suites, so every reply but the byte-exact one scored as a miss, and the guard now probes the nesting in **both** directions so the contained choice stays reachable, plus the **by-design residue** it pins: for a nested pair containment is the only evidence available, so an unbracketed enumeration resolves to the *longer* choice instead of reading as ambiguous — a real trade, taken deliberately, and asserted so it cannot be "fixed" back by re-breaking the line above it; a miss prints the model's **raw reply**, since a line showing only the parsed label cannot distinguish a wrong answer from a wrong parse; and the rubric travels as a `cache_control: ephemeral` system block, byte-identical across a suite's cases, for ~80% off the input bill at no change to any answer (the run's last line reports cache reads/writes, and distinguishes the two reasons there might be none: `cache not applicable` when the prompt is under the ~1024-token minimum cacheable prefix — true of the three smallest suites, where there is nothing to discount and nothing to fix — and `cache MISSED` only when a prompt long enough to cache produced no cache activity anyway, which is the one worth investigating; the first CI run confirmed the README's prediction of exactly which three suites cannot benefit, and showed that the undifferentiated `MISSED` wording was sending readers after a non-existent defect). Cache reads and writes are metered under their own `gen_ai.token.type` values and never summed into `input` — a read bills at 0.1× and a write at 1.25×, so one total misreports the cost in both directions. The first real nine-suite baseline (130/140 = 92.9%, ~$0.77 uncached → ~$0.30 with the cache) and its four findings — including the run-to-run variance (±2 cases at n=22 is ±9 points, so never gate on regression-vs-baseline at these sizes) and the fact that the raw-reply line REFUTED the tempting scorer explanation for `tier-routing`'s five misses, which are genuine rubric under-tierings — are recorded in [`scripts/eval/README.md`](../scripts/eval/README.md#the-l2-baseline--first-real-run) — compare against it rather than a remembered number. **The first full run in CI scored 131/140 = 93.6%** (both totals are over the pre-decoy 140-case population; nine suites are **149** cases now, so neither aggregate is comparable to a current run — compare per suite), one case above that baseline, and its composition is the lesson: `tier-routing` gained 5 from a rubric fix while four untouched suites each drifted −1 or −2, so the aggregate barely moved across the most substantive rubric change in the repo's history. Never read the total as a quality signal, and treat a single post-fix suite figure as directional only — two of the three re-measured suites came back a case worse in CI than locally, with nothing changed but the sample. Add a suite: golden JSONL + a `SUITES` entry in `scripts/eval/suites.mjs` — and nothing else, because **CI selection is DERIVED from that table, never mirrored**: `select-suites.mjs` maps the PR's changed files to suite names off each suite's own `rubric.file` / `golden`, a `select` job emits them as a matrix, and one job runs per affected suite via the existing `--suite` flag. A harness file (`l2.mjs`, `lib.mjs`, `suites.mjs`, `select-suites.mjs`) selects **all** suites — the deliberate fail-open direction, since extra suites cost tokens while a missed suite costs coverage and reports as a green PR either way. The workflow's hand-written `paths:` filter is gone: it had drifted to four of nine rubric files missing (`severity/SKILL.md`, `optimality-rubric.md`, `depth-routing.md`, `rubric-composition.md`) plus two paths backing no suite, so those four rubrics could be edited with their own eval never running — the same reason `READ_TOOLS` is held to the tool catalog by assertion rather than restated. `G21d` asserts the derivation **and** the absence of a rubric-path mirror; `G21h` executes the selector's self-test (each suite selected by its own rubric and golden file, a harness file selecting all, a near-miss selecting none) and asserts `l2.mjs` exits non-zero on an unknown `--suite`, since CI drives that flag from a generated matrix and a run-nothing-exit-0 would report a typo as a passing eval. Require the aggregator check **`evals · L2 (behavioral) / l2`**, which runs on every PR (`if: always()`) — never a per-suite job, which comes and goes with the diff and would leave a required check pending forever. The `code-review-retrieval-relevance` suite (PR B2) measures whether `pr-reviewer`'s documented Step 1.0 + 1.2c read surfaces the right lessons for a given diff; ground truth is the outcome signal (`loop::reviewer-lessons` / `loop::reviewer-comment-relevance` + `seen_count >= 3`), with a BOOTSTRAP SEED golden set (not a real baseline — real corpus is hosted-only). Its rubric is `### 1.0` **+** `### 1.2c`, deliberately not their `## Step 1` parent: `extractSection` is heading-level-aware, so the parent fed all ten `### 1.x` subsections (67,630 chars vs. 27,568), and the one that decides it is `### 1.2d`, whose diff-keyed shortlist answers *what reaches the finders* rather than *what the documented read returns* — with it in scope, a list-reachable lesson unrelated to the diff is legitimately `skip` and the suite contradicts its own `instruction` string. `G21a` reds on a re-widening. **Its two seed-set limitations were closed by decoys, never by moving the floor** — the set is now 14 cases, 8 `surface` / 6 `skip`, a 57.1% majority-class baseline (it was 4/1 and 80%, where an always-`surface` responder cleared the 70% floor, so a green meant only "the model stopped answering `skip`"; and at N=5 one miss was 80% pass and two was 60% fail, so the floor's own "only trips on a badly-broken rubric" justification did not hold — 14 cases also puts it above `EVAL_GATE_MIN_CASES`, so it gates rather than reporting `[advisory]`). L1 **`G21n`** asserts the baseline sits below the floor, deriving the labels from the JSONL and the floor from `evals-l2.yml` rather than re-encoding either, so re-degenerating the split reds L1 instead of only a paid L2 run — and because every `diagnose` promotion adds a `surface` case, that guard reds *by design* as promotions drift the balance: pair one with a decoy, never relax the guard. (Numbered `G21n`, not `G21h`: this guard and the suite-selector self-test arrived on separate branches both claiming `G21h`.) **The six `skip` decoys are derived from the read's own four filter dimensions**, one per dimension so each is unanswerable without the rubric — tag (`codebase-knowledge`, read at Step 1.2a and by neither path in scope), scope (`branch::`, and a different repo's `repo::` with a deliberately on-topic gist), expiry, and source attribution (`source.agent: 'aw-executor'`), with `global` and `source.explicit: true` as positive counterparts so scope and attribution are tested in both directions. The two persistently-missed originals were **not edited**: they got explicitly-scoped superseding twins and stay runnable as regression guards. **The `instruction` was the third lever, and the framing rather than the rubric was the target** — the prior wording asked whether the record "would be surfaced by the documented read *for the given PR diff*", a relevance question the rubric itself calls a defect, and the model answered `skip` on a run where that sentence was already in front of it; the verb is now `surfaces`, matching the labels, because Step 1.0's source-attribution filter runs on what its calls *returned* and under "returns" the two attribution cases were answerable both ways. Fixing that exposed a self-contradiction in the rubric — `### 1.0` said its four calls "filter on three things and nothing else" while rule 1 of the same section binds `source.agent` on every read it issues — now resolved by naming attribution as the fourth filter and stating where it runs, alongside a statement that the `scope` parameter matches exactly (`m.scope = p_scope`) rather than as a prefix or a hierarchy. `--suite` itself takes a **comma list** so one process can run a selected subset, and each way of naming nothing has its own exit code rather than a shared one: an unknown name exits 2 and lists the suites, an **empty** selection exits 5 (CI passes a computed value there, so `""` is the likeliest spelling of a selector bug and would otherwise grade zero cases and report a pass), an absent key under `EVAL_REQUIRE_KEY` exits 3, and a missing or empty golden file exits 4. **An L2 run also emits OTLP traces and metrics** ([`scripts/eval/telemetry.mjs`](../scripts/eval/telemetry.mjs), zero-dependency `fetch`, one flush at exit), because stdout answers *what was today's accuracy* and cannot answer *has this rubric been drifting for three weeks* or *which suite is eating the token budget* — both are trend questions and a trend needs a backend. Shape: `eval.run` → `eval.suite <name>` → `eval.case <id>` (CLIENT) spans, plus `eval.case.result` (Sum, delta, split by `eval.case.match`, so accuracy is a backend-side ratio), `eval.suite.accuracy`/`eval.run.accuracy` (Gauge, `%`), `eval.case.duration` (Histogram, `s`) and the upstream-semconv `gen_ai.client.token.usage` (Histogram, `{token}`, split by `gen_ai.token.type`). Four rules, all guarded by `G21k` and each probed by breaking it: **off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set** (a fork or fresh clone attempts no export); **a MISS is not a span error** — a wrong answer is the measurement, so the case span stays `UNSET` and only a transport/API failure sets `ERROR`, since conflating them makes every rubric regression look like an outage in the trace list; **an absent attribute is omitted, never a placeholder** (`unknown` is not queryable as absent); and **the flush precedes the gate exit**, so a run that trips `EVAL_GATE` still ships the trace you most want to read — asserted positionally, because a refactor that moves the exit up would lose exactly that trace. Export failure never changes the verdict: the accuracy is the product, the span is the receipt. In CI the endpoint is a repo **variable** (a hostname is not a secret) and only `DASH0_AUTH_TOKEN` is a secret; each matrix job is its own process, so an opted-in PR yields **one trace per suite** — group by the `cicd.pipeline.run.id` resource attribute.
- **L2-detection — does the reviewer actually find the bug** (`ANTHROPIC_API_KEY=… node scripts/eval/l2-detection.mjs`, `--self-test` runs offline and is executed by L1 `G39`): a **separate** runner, because the classification runner above cannot express detection. It asks a single-choice question with `max_tokens: 16` and exact-matches the answer, so the only detection question it can pose is "is there a bug here, yes or no" — and a reviewer that answers yes to everything scores 100 % recall on it. This runner replays the real two-pass pipeline per record: the finder over the diff (reading [`finders.md`](../agents/pr-reviewer/rules/finders.md) live as its system prompt), then the verifier over each candidate it returns (reading [`finding-verifier.md`](../agents/shared/rules/finding-verifier.md) live). A candidate counts as a hit only when its path matches, its line is within `LINE_TOLERANCE = 3`, **and** the verifier confirmed it — an unparseable verdict is never read as a confirmation. Gates are `recall ≥ 0.7` and `fp ≤ 0.2`, so recall and precision are measured together and neither can be bought with the other. `golden/bug-detection.jsonl` holds 50 records — 20 seeded, four each of `logic`, `consumer-break`, `dep-breaking-change`, `intent-mismatch`, and `standards`, plus **30 controls, every one a decoy** (a seeded record with the defect removed, a fix mistakable for the bug it fixes, a rule applied where it is scoped out, a break whose usage sites the same diff already updates) so the false-positive rate measures discrimination rather than diff difficulty. **The controls grew from 10 to 30 to make `fp_rate` measurable at all** — one control was 10 points against a 20-point gate, so the metric had four usable states and could not distinguish a real precision improvement from run-to-run variance; at 30 a dirty control is 3.3 points and the gate tolerates 6, asserted by the self-test as `floor(controlN × GATES.fp) >= 4`. The fix for that assertion is always MORE CONTROLS: lowering `GATES.fp` shrinks the tolerated count, so it makes the resolution worse while looking like a concession. Consequence for the recorded runs: every `fp_rate` in the five-run baseline is over a 10-control denominator and is **not comparable as a number** to a current run's. `validate()` rejects a golden file whose defect path appears in no surface the finder is shown, which is the defect that makes a recall number meaningless. A promoted `detection::<finder>` lesson becomes a seeded case here. **It now runs in CI, in its own `bug-detection` job, and gated** — it previously ran in *no workflow at all*, so only its `--self-test` executed and the scoring plumbing was guarded while the measurement had never once run. Selection rides the same derivation as the nine suites without becoming a matrix entry (it cannot ride `--suite`): `SUITES.DETECTION` in `suites.mjs` declares the runner, the two live rubric files and the golden set, `select-suites.mjs` reports one extra boolean off that declaration, and the job consumes it — a harness change selects both it and every suite (fail-open), a `finders.md` edit selects it and no suite, a suite rubric selects a suite and not it. Unlike the suites' soft `EVAL_GATE` floor it runs with `EVAL_DETECTION_GATE=1`, because the two rates *are* its contract. `G21m` asserts the chain end to end, and the last link is the load-bearing one: the `l2` aggregator is `if: always()`, so a failed dependency reaches it as a value to *read*, and an aggregator reading only `needs.suite.result` is how a red detection run reports green (`skipped` stays a pass on either job — a PR can affect one eval and not the other). **Its first five runs measured recall 75/60/70/75/90% and fp_rate 30/40/30/≤20/40%** (all over the pre-growth 10-control denominator) on the detection core as it already stood — red in four of five, and that is the eval working, not a regression the change that permitted it introduced. Findings in [the detection baseline](../scripts/eval/README.md#the-l2-detection-baseline--the-first-three-runs), and the first one is a **retraction**: run 1 appeared to show the verifier halving the finder's false positives (50% → 30%) at *zero* recall cost — `finders.md`'s flag-then-filter polarity measured rather than argued — but run 2 shows it spending 20 points of recall for 10 of precision, a NEGATIVE lift, and run 3 comes back looking like run 1 (−10 fp at −0 recall). Two of three runs show the polarity working and one shows it inverted, across a lift spread of −10 to +20 — which at 20 seeded records (one case = 5 recall points) and 10 controls (one control = 10 fp points) is the entire spread, so **the verifier's value is not established** and no single detection run may be quoted for or against it. What the runs DO establish is that the controls are where the work goes — four of five failed on `fp_rate` while recall straddles its 70% bar, and once itemised the survivors turned out to be the controls' own defects (see below) — and that repeats are needed before and after any rubric edit. What they do **not** establish is that the precision gap is *reproducible*: an earlier reading called it that on the strength of 30/40/30, and run 4 came in at or under the gate before run 5 went back to 40, so one meet in five is a flaky gate rather than a standing red. Runs 4 and 5 are a clean same-content pair (both on a diff touching neither rubric), so the spread between them is pure variance — which is the observation the control growth above answers. `intent-mismatch` is the weak class in both (1/4 then 2/4 against 3/4–4/4 elsewhere) with most misses never flagged, so that gap is finder recall rather than verifier over-filtering; and one record failed on output *shape* (the finder replied prose instead of JSON), counted as a miss and never as clean — never loosen the parse to recover it. Raising the core's precision means editing the two rubrics this eval measures, so it needs its own golden decoys and its own re-run; lowering the gate to meet the current core is the fix-to-pass forbidden everywhere else here, and is what left the eval unrun to begin with. **Runs 6 and 7, the first two on the 50-record set, both PASSED** (recall 90%/80%, fp 20%/17%, lift +13/+20) — and run 7, the first to print its surviving controls BY NAME rather than as a count, overturned the planned next step: four and a half of the five false positives were **defective fixtures**, not verifier failures. The finder was correct that a control's `shallowClone` spread primitives, that another used `Future` with no import, that a "clean" perf diff introduced module-level state and an unenforced call ordering, and that a `mockReset()` break in a test file is still a break (the record's own "it is only a devDependency" premise was wrong). Two of the four were ORIGINAL controls carrying defects invisible for the whole recorded baseline. Tuning `finding-verifier.md` against them would have taught it to reject TRUE findings while `fp_rate` went down — the same fix-to-pass one level up, and much harder to spot. So the fixtures were repaired and the rubrics were left alone; the evidence that the verifier works is in the same output, dropping 6 of 11 flagged controls, every rescue a well-formed decoy. Two rules follow: **a control asserting "this diff is clean" is a claim about the WHOLE diff, not about the one thing it probes** (four of five probed correctly and were dirty for an unrelated reason), and **`fp_rate` alone cannot tell an over-permissive verifier from a defective control set** — five runs of a bare number pointed at the rubric, one run of named survivors pointed at the fixtures, so never tune a rubric against a rate you have not itemised. **Runs 8 and 9, the two after the repair, both came in at fp 10% (3/30) against 6 tolerated with recall unchanged at 80%** — the first readings with real margin, bought by fixing fixtures rather than by touching a rubric or the gate. Run 9 is a TRUE repeat (its commit changes only prose, so fixtures, both rubrics and the runner are byte-identical), and the agreement on the headline is the confirming repeat the standing rule asks for — but **the three controls behind the number are not the same three**, which is the finding: two survivors are stable, and two swapped across the verifier boundary (`control-off-by-one-that-is-correct` rescued, `control-description-matches-larger-diff` newly dirty at 2 of 2 candidates). So itemising was not optional — two runs agreeing on a bare `10%` would have read as a stable operating point while a third of it moved, and the move pointed at a defective fixture the run-7 write-up had used as evidence FOR the core: the finder is right that `{ ...u, email: u.email, phone: u.phone }` is identical to `u`. That makes six over-loaded fixtures found, three of them ORIGINAL controls; repair it next, with `control-off-by-one-that-is-correct`'s missing consumer surface ("no callers were migrated" is unanswerable from what the finder is shown). `lift` moved +12 → **+5** on identical inputs (the finder alone came in at 30% fp instead of 20% while the post-verifier result did not move), so the retraction above stands unamended. **Run 10, the third post-repair pass and the second true repeat, came back at recall 70% — EXACTLY the gate — with fp 7% (2/30)**, so the three post-repair runs read 80/10, 80/10, **70/7** on byte-identical fixtures. Recall moved 10 points on identical inputs, which is the SAME defect the control growth just fixed, on the other half of the set: at 20 seeded records one case is 5 recall points against a 70% gate, so a rubric edit worth under ~10 points is indistinguishable from sampling, and two runs reading 80% looked like a comfortable margin while the third sits on the line. **So the next instrument fix is GROW THE SEEDED HALF, and it outranks the `intent-mismatch` work** — same argument as the controls (never tune a rubric against a number that cannot express the change), and the runner's own comment predicted it before the measurement arrived. Secondary, all on identical fixtures: `consumer-break` fell 4/4 → 2/4 (both never flagged), so a class can look solved for two runs and swing by two; `intent-mismatch` is the weakest class on average across eight runs (1/4, 2/4, 2/4, 4/4, 2/4, 1/4, 3/4, 1/4) with most misses **never flagged**, so it is finder recall rather than verifier over-filtering, but no single run's reading of HOW weak is usable; and one record failed on output SHAPE again (the finder replied prose instead of JSON), counted as a miss and never as clean — never loosen the parse to recover it. `fp_rate` continues to fall (10 → 10 → 7) with only the two known borderline originals surviving, so precision is not what is unmeasurable here — recall is.
